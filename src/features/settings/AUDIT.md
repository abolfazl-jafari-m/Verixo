## Implementation plan

- Central `features/settings` schemas/defaults/selectors and a versioned browser-local adapter; section-scoped reads/writes and notifications, no new state library or fake API.
- Five accessible URL-backed tabs using the installed Base UI Tabs primitives (no Tabs wrapper currently exists). Existing `/settings/shipping-labels` remains a compatible redirect to the shipping tab.
- Shared bilingual shop name/logo/contact; shipping can opt into a separate dispatch contact, never a second shop identity. Legacy sender settings migrate read-only until the first central Save, then the central record wins. Corrupt data is reported and never silently overwritten.
- Reuse RHF/Zod, existing input/select/switch/dialog/toast, logo decoding and next-themes/next-intl. Explicit section Save/discard and recoverable session drafts; appearance choices are immediate.
- Snapshot central invoice presentation only for new invoices, retaining the old seed for old fixtures/legacy invoice migration. Render saved logo/contact from the snapshot. Apply report/label defaults only when opening a fresh view.
- Unit/component and browser verification for persistence failures, migrations, shared/override precedence, historical protection, dirty state and RTL/LTR.

## Implemented integration map

`model.ts` owns typed defaults, schemas and pure snapshot/sender selectors. `storage.ts` owns independent `verixo:settings:v1:{shop,invoices,shipping,reports}` records; it reads the old shipping key only when the corresponding central record is absent and never rewrites legacy orders. `use-settings.ts` subscribes to its section only. `drafts.ts` stores recoverable tab-local session drafts separately from saved values.

`components/settings-tabs` owns URL/keyboard tab behavior; `section-editor` owns validation, Save/discard, storage error/retry and unsaved navigation protection. Existing logo decoding, controls and form libraries are reused. No dependencies were added. `/settings` composes the tabs, while `/settings/shipping-labels` remains a redirect. The sidebar and public customer-information header consume `ShopIdentity`. New OrdersProvider issuance reads validated settings and freezes them through `createMockInvoice`; invoice rendering reads only snapshots, now including an optional logo for backward compatibility. Corrupt/unreadable shop or invoice settings block new issuance rather than freezing fallback identity. Shipping's former editable store/form is replaced by a read-only resolver over central settings. ReportProvider initializes from saved report preferences without overwriting an active range. Theme and locale still use their existing providers/router.

Concurrent edits to different sections are isolated; same-section simultaneous saves use last-write-wins until backend revision checks exist. Pristine forms refresh on storage/focus updates; dirty forms keep local edits. Draft recovery is best effort if session storage is unavailable. No setting changes order status, historical costs, historical invoice branding or financial coverage.

## Backend boundary

All business settings remain local to this browser and origin. Public mock pages only see this browser's data; Laravel must supply authorized shop settings and public invoice snapshots. Replace the storage adapter with authenticated reads/section updates, durable logo storage, server-side validation and immutable issuance snapshots. Theme/locale are personal preferences, not merchant business settings. Existing product session persistence and financial data completeness are unchanged.
